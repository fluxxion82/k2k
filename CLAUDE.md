# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project overview

k2k is an experimental Kotlin Multiplatform peer-to-peer library — a Ktor-based rewrite of [DATL4G/Klient2Klient](https://github.com/DATL4G/Klient2Klient) exploring UDP socket discovery and packet transfer between devices on the same LAN. The repo bundles the library with example apps that exercise it on three platforms.

Despite living under a `passwordManager/` parent directory, this codebase is the p2p library itself; nothing here implements password management.

## Modules

| Module | Type | Purpose |
|---|---|---|
| `k2k` | KMP library (jvm + iosArm64 + iosSimulatorArm64) | Core p2p: discovery (UDP broadcast) + connection (TCP/UDP send-receive). Public API entry points are `Discovery.Builder` and `Connection.Builder` in `commonMain`. Exposed to iOS via CocoaPods as `k2k.framework`. |
| `presenter` | KMP library (jvm + ios) | Shared ViewModel/presenter layer (`MainPresenter`) consumed by all three example apps so platform UIs stay thin. Uses KMP-NativeCoroutines for iOS interop. |
| `desk` | JVM + Compose Desktop app | Example desktop app, `MainKt` entry point. |
| `droid` | Android app (minSdk 28, targetSdk 34, compileSdk 35) | Example Android app, Compose Material3. Acquires a WifiManager multicast lock on Start. |
| `ios` | Xcode project (Swift/SwiftUI) | Example iOS app. Builds via CocoaPods consuming the `k2k` and `presenter` podspecs generated by Gradle. |

`desk` and `droid` both build off `presenter`, which builds off `k2k`. The iOS app consumes `k2k` and `presenter` as Cocoapods.

## Common commands

All Gradle commands run from the repo root. JVM target is 17; Kotlin 2.1.20; AGP 8.9.1.

```bash
# Build everything
./gradlew build

# Run the desktop example
./gradlew :desk:run

# Install Android example on a connected device/emulator
./gradlew :droid:installDebug

# Tests
./gradlew test                           # all modules
./gradlew :k2k:jvmTest                   # k2k JVM tests only
./gradlew :k2k:jvmTest --tests "ClassName.methodName"   # single test

# iOS — must run before opening Xcode after Gradle changes:
./build_pods.sh
# (equivalent to: ./gradlew -p k2k podspec && ./gradlew -p presenter podspec && pod --project-directory=ios install)
# Then open ios/ios.xcworkspace in Xcode and build/run there.
```

There is no separate lint task configured; `./gradlew check` runs the standard verification chain.

## Architecture notes

### Network discovery flow
- `DiscoveryClient` (UDP broadcast sender) and `DiscoveryServer` (UDP listener) in `k2k/src/commonMain/.../discover/` are `@ThreadLocal object` singletons — there is a single shared instance per platform thread/process. The public `Discovery` class wraps them with a Builder API.
- `Discovery.makeDiscoverable()` starts broadcasting a serialized `Host` over the configured UDP port every `ping` ms (default 1000). `Discovery.startDiscovery()` binds the same port and accumulates discovered hosts in `DiscoveryServer.hosts` (a `MutableStateFlow<Map<Host, Long>>`), evicting entries older than `puffer` ms.
- `Host` is the unit of identity: `name` + `filterMatch` are serialized over the wire; `hostAddress` and `port` are `@Transient` and populated from the inbound datagram's `InetSocketAddress`.
- `NetInterface` is an `expect object` resolved per-platform — JVM uses `java.net.NetworkInterface`; iOS/native has its own actual.

### Connection flow
- After discovery surfaces a peer, `Connection.Builder` is constructed with the peer set (commonly from `discovery.peersFlow` or a single host) and a port. `Connection.send()` opens a TCP socket to the peer; `startReceiving()`/`receiveData` flow let one side act as a server.
- Discovery and connection use **different ports** by convention. `MainPresenter` uses 1337 for discovery and 2323 for connection.

### Presenter pattern
`MainPresenter` (in `presenter/`) owns a `SupervisorJob`-backed `CoroutineScope`, drives the `Discovery`/`Connection` lifecycles, and exposes `foundPeers: MutableStateFlow<List<Host>>`. The desktop and Android apps subscribe via `collectAsState()`; iOS uses `@NativeCoroutinesState` (KMP-NativeCoroutines plugin) for Swift/SwiftUI interop. Constructor flag `receiving: Boolean` switches the example between server (collect data) and client (send "Hello world") roles — `desk` is `true`, `droid` is `false`.

### Dependency versions
All versions are pinned in `gradle/libs.versions.toml` (version catalog). Update there, not in individual `build.gradle.kts` files.

## Known issues (from README)

- iOS shows up as discoverable to desktop/Android but its own `DiscoveryServer.hosts` flow doesn't populate, so the iOS UI list stays empty. Tracked upstream at [KTOR-6489](https://youtrack.jetbrains.com/issue/KTOR-6489).
- "Address already in use" exceptions appear frequently when stopping/restarting on the same port — this is expected current behavior, not a regression to fix incidentally.
- iOS can crash if the desktop app starts discovery first.

## iOS gotchas

- The `kotlin.code.style=official`, `kotlin.incremental=false` settings in `gradle.properties` are intentional for KMP/native builds.
- The presenter's iOS target chooses arch from `SDK_NAME` / `NATIVE_ARCH` env vars at Gradle configure time — Xcode sets these when invoking Gradle; running `./gradlew :presenter:build` from a terminal will default to `iosX64`.
- Re-run `./build_pods.sh` whenever Kotlin source in `k2k` or `presenter` changes signatures the iOS app depends on; `pod install` alone is not enough.
